# MQTT Connection and Memory Allocation Fix - 2026-05-14

## Issues Addressed

### 1. MQTT Connection Failure Handling
- **Problem**: The application would terminate with a fatal error if the initial MQTT connection failed.
- **Solution**: 
    - Modified `epaper_bulletin.py` to make initial MQTT connection errors non-fatal.
    - Enhanced `bmp_display.py` with `draw_text` and `draw_error` methods.
    - If MQTT fails to connect at startup, the e-paper display now shows "MQTT Connection Failed" and the application continues to the main loop.
    - The main loop will automatically attempt to reconnect to the MQTT broker periodically.

### 2. Memory Allocation Error in MQTT Library
- **Problem**: Logged error `memory allocation failed, allocating 4294967293 bytes`.
- **Diagnosis**: This occurred in `umqtt/simple.py`. When a malformed or partial MQTT packet was received, the calculation `sz -= topic_len + 2` could result in a negative number. When passed to `socket.read(sz)`, MicroPython interpreted this negative signed integer as a very large unsigned integer, leading to a massive (and failing) memory allocation attempt.
- **Solution**: 
    - Patched `umqtt/simple.py` to validate the message size (`sz`) before attempting to read the message body.
    - If `sz` is negative or exceeds a reasonable limit (65535 bytes), it now raises an `OSError`.
    - This allows `mqtt_handler.py` to catch the error, mark the connection as lost, and trigger a reconnection attempt instead of crashing the system.

## Files Modified
- `epaper_bulletin.py`: Changed initialization logic and added error reporting to display.
- `bmp_display.py`: Added text rendering and error screen support.
### 5. Chunked File Streaming
- **Problem**: Even with basic optimizations, reading 48KB into RAM at once is risky on the Pico W.
- **Solution**: 
    - Rewrote `umqtt/simple.py` to stream payloads directly to a temporary file (`temp_mqtt_msg.bin`) in 1KB chunks.
    - The MQTT callback now receives a filename instead of a large bytes object, keeping RAM usage extremely low and constant regardless of message size.

### 6. Multi-Topic Support (BMP & Binary)
- **Design**: The system now supports two distinct update channels:
    - `{topic}/binary`: For raw 48,000-byte pixel buffers (fastest).
    - `{topic}/bmp`: For standard BMP image files (flexible).
- **Auto-Detection**: `BMPDisplay` now automatically detects the file format by checking the magic bytes and chooses the appropriate rendering method.
