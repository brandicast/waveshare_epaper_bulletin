# 經驗總結與錯誤檢討 (Lesson Learned - 2026-05-14)

在本次開發 Session 中，我們針對 7.5 吋三色電子紙佈告欄系統進行了深度優化。過程中遇到了一些關鍵技術挑戰與錯誤，以下是總結與檢討。

## 1. 記憶體管理 (RAM Management)
- **錯誤案例**：在處理 24-bit BMP 渲染時，因採用巢狀方法呼叫導致同一個檔案被 `open()` 兩次。
- **後果**：多佔用了約 10KB 的檔案緩衝區，導致 Pico W 出現 `ENOMEM` (記憶體不足) 錯誤。
- **教訓**：在資源受限的系統（如 MicroPython）中，**檔案控制權 (File Handle) 必須嚴格管理**。應儘量統一解析路徑，避免重複開啟檔案與多層級遞迴呼叫。

## 2. 網路協定與裝置相容性
- **錯誤案例**：WiFi 配網伺服器原本僅簡單使用 `cl.recv(1024)` 讀取請求。
- **後果**：iPad Safari 等行動瀏覽器常會分次發送 Header 與 Body，導致後端解析不到 POST 資料，顯示 "Invalid Data"。
- **教訓**：網路通訊不能假設一次 `recv` 就能拿到所有資料。必須**檢查 Content-Length 並循環讀取**直到 Body 完整，才能保證跨裝置的相容性。

## 3. 畫面顯示邏輯
- **錯誤案例**：簡化渲染器時，漏掉了在顯示 1-bit BMP 前清空紅色緩衝區。
- **後果**：當從三色圖切換回黑白圖時，螢幕上會留下前一張圖的紅色殘影（Ghosting）。
- **教訓**：三色螢幕擁有獨立的黑、紅緩衝區。**任何渲染動作開始前，都應明確重置所有相關緩衝區**，確保畫面內容的純淨。

## 4. 環境依賴性假設
- **錯誤案例**：假設主機端 (User Host) 一定有安裝 `Pillow` 函式庫來執行 `bmp_gen.py`。
- **後果**：在自動化腳本執行時因缺少套件而失敗。
- **教訓**：工具鏈開發應具備**環境感知與備援機制**。例如，當偵測到無 Python PIL 時，應能自動切換使用 `ffmpeg` 等系統級工具作為替代方案。

## 5. Web UI 的反饋機制
- **錯誤案例**：在 `index.html` 中使用了過於樂觀的 UI 更新（Submit 即顯示成功）。
- **後果**：掩蓋了後端接收失敗的真相，導致使用者誤以為設定成功。
- **教訓**：**前端狀態應儘可能由後端真實響應觸發**。改用後端回傳包含 Success 樣式的 HTML 才是最穩健的做法。
