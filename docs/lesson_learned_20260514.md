# 經驗總結與錯誤檢討 (Lesson Learned - 2026-05-14)

在本次開發 Session 中，我們針對 7.5 吋三色電子紙佈告欄系統進行了深度優化。過程中遇到了一些關鍵技術挑戰與錯誤，以下是總結與檢討。

## 1. 記憶體管理 (RAM Management)
- **錯誤案例**：在處理 24-bit BMP 渲染時，因採用巢狀方法呼叫導致同一個檔案被 `open()` 兩次。
- **後果**：多佔用了約 10KB 的檔案緩衝區，導致 Pico W 出現 `ENOMEM` (記憶體不足) 錯誤。
- **教訓**：在資源受限的系統（如 MicroPython）中，**檔案控制權 (File Handle) 必須嚴格管理**。應儘量統一解析路徑，避免重複開啟檔案與多層級遞迴呼叫。

## 2. 網路協定與裝置相容性
- **錯誤案例**：WiFi 配網伺服器原本僅簡單使用 `cl.recv(1024)` 讀取請求。
- **後果**：iPad Safari 等行動瀏覽器常會分次發送 Header 與 Body，導致後端解析不到 POST 資料，顯示 "Invalid Data"。
- **教訓**：網路通訊不能假設一次 `recv` 就能拿到所有資料。必須**檢查 Content-Length 並循環讀取**直到 Body 完整，才能保證跨裝置的相容性。

## 3. 畫面顯示邏輯
- **錯誤案例**：簡化渲染器時，漏掉了在顯示 1-bit BMP 前清空紅色緩衝區。
- **後果**：當從三色圖切換回黑白圖時，螢幕上會留下前一張圖的紅色殘影（Ghosting）。
- **教訓**：三色螢幕擁有獨立的黑、紅緩衝區。**任何渲染動作開始前，都應明確重置所有相關緩衝區**，確保畫面內容的純淨。

## 4. 環境依賴性假設
- **錯誤案例**：假設主機端 (User Host) 一定有安裝 `Pillow` 函式庫來執行 `bmp_gen.py`。
- **後果**：在自動化腳本執行時因缺少套件而失敗。
- **教訓**：工具鏈開發應具備**環境感知與備援機制**。例如，當偵測到無 Python PIL 時，應能自動切換使用 `ffmpeg` 等系統級工具作為替代方案。

## 5. Web UI 的反饋機制
- **錯誤案例**：在 `index.html` 中使用了過於樂觀的 UI 更新（Submit 即顯示成功）。
- **後果**：掩蓋了後端接收失敗的真相，導致使用者誤以為設定成功。
- **教訓**：**前端狀態應儘可能由後端真實響應觸發**。改用後端回傳包含 Success 樣式的 HTML 才是最穩健的做法。

## 6. 三色電子紙與快速刷新模式 (Fast Mode) 衝突
- **錯誤案例**：為了加快按鍵測試的反應速度，對 7.5 吋三色 (B) 電子紙啟用了 `mode="fast"`。
- **後果**：畫面上充滿了紅色、白色與黑色的隨機雜訊點（雪花），無法顯示正常圖像。
- **教訓**：三色電子紙的紅色粒子需要特殊的驅動波形與較長的沉澱時間（通常需 15 秒）。**絕對不能對三色電子紙使用專為黑白螢幕設計的 fast 模式**，否則會導致粒子無法正常分離。開發時必須使用 `mode="normal"`。

## 7. 電子紙 FrameBuffer 清除與實體刷新的分離
- **錯誤案例**：在準備繪製新畫面時，呼叫了原廠驅動的 `epd.clear("white")` 來清空背景，接著在 RAM 畫圖，最後又呼叫 `epd.display()`。
- **後果**：`epd.clear()` 底層不僅清空了 RAM，還自動呼叫了一次實體 `display()`。這導致螢幕先是長時間刷新成全白，接著又立刻被要求刷新文字，造成連續兩次物理刷新，引發顯示異常與閃爍卡死。
- **教訓**：**RAM 緩衝區操作與實體螢幕刷新必須嚴格分離**。在繪圖流程中，應直接操作 `epd.imageblack.fill(1)` 與 `epd.imagered.fill(0)` 來重置記憶體，等所有物件畫完後，再執行「唯一一次」的 `epd.display()`。

## 8. 實體按鍵 GPIO 映射與硬體重置限制
- **錯誤案例**：在設計規劃中，假設驅動板有 3 顆完全可程式化的按鍵（配置為 GPIO 15, 17, 2）。
- **後果**：測試時發現第一顆按鈕沒有任何反應，且按下第三顆按鈕時會直接導致 Pico W 重新啟動並中斷 USB 連線。
- **教訓**：**實體電路設計與針腳定義必須先經由硬體測試驗證，不能單憑假設**。此 Waveshare 7.5inch e-Paper 驅動板實際上僅有兩顆可程式化按鍵，分別接在 **GPIO 3 (Top)** 與 **GPIO 2 (Middle)**；而最下方的第三顆按鈕是硬體寫死的 **RUN (Reset) 重置鍵**。在進行軟體與低功耗設計時，必須牢記此硬體限制，並將功能重新收斂與設計。

## 9. SPI 通訊的深眠死鎖與 Timeout 安全防護
- **錯誤案例**：在進行效能分析時，程式在送出第一張圖的更新命令後，立刻呼叫了 `epd.sleep()` 讓螢幕進入深層睡眠；隨後立即測試第二張圖，結果導致程式永久卡死。
- **後果**：電子紙在深眠狀態下不會回應任何 SPI 指令和硬體狀態，導致驅動程式底層 `_wait_until_idle()` 的無窮迴圈 `while busy == 0` 被永遠鎖死（Deadlock）。而若強制在 16-20 秒的實體刷新期間中呼叫 `sleep()`，也會強制切斷高壓驅動源，導致畫面「完全沒動」。
- **教訓**：
  1. **測試與連續刷新時嚴禁提早 Deep Sleep**：必須確保所有硬體互動都結束後，才能在 `finally` 區塊中進行唯一一次的深眠。
  2. **必須實作 Timeout 機制**：原廠驅動的 `_wait_until_idle()` 存在設計缺陷，**所有等待硬體回應的 `while` 迴圈都必須加入安全超時（Timeout）防護**。我們已將其修改為 40 秒安全超時，徹底根除了因為硬體掉線或深眠而導致整個系統卡死的問題。

## 10. 微控制器檔案系統 (LFS) 容量與圖片大小的物理極限
- **錯誤案例**：透過終端機指令（cp）與 IDE 嘗試將一張 376KB 的 8-bit Indexed BMP 複製到 Pico W，結果屢次出現 `timed out or error in transfer to remote: b'F'` 的錯誤。
- **後果**：檔案無法上傳，導致 Pico W 上一直執行的是舊版的 47KB 圖片。
- **教訓**：MicroPython 在分配完系統核心後，Pico W 大約僅剩 **303 KB** 的實體 Flash 空間。**檔案傳輸失敗並非通訊問題，而是物理磁碟已滿（Disk Full）**。在開發嵌入式系統時，必須時刻精算儲存空間。最終我們開發了 ** Raw 2-bit Binary (.bin, 僅 96KB)** 作為終極解法，完美避開了所有硬體與記憶體限制。

## 11. MQTT 封包限制與 Robust 重連機制的訂閱遺失陷阱

- **錯誤案例**：發送 96KB 的三色 binary 影像檔時，主機端並未崩潰但後續再也收不到任何 MQTT 訊息，主程式狀態持續顯示 `Errors: 0`，但終端機印出 `[umqtt] ERROR: Message too large: 96000`。
- **後果**：
  1. `lib/umqtt/simple.py` 中寫死了 `65535` 位元組的封包長度限制。當 96,000 位元組的 3-color binary 封包到達時，觸發該限制並丟出 `OSError(-1)`。
  2. 此 `OSError` 被 `lib/umqtt/robust.py` 內部的 `check_msg()` 自動捕捉。`robust.py` 會默默進行 `reconnect()`（在 `DEBUG = False` 下無聲執行），但重連時僅呼叫 `super().connect(clean_session=False)` 重建 Socket 連線，**並未重新訂閱主題**。
  3. 由於異常在內部被攔截並完成了 socket 重連，對外（`core/mqtt_handler.py`）來說，`check_messages()` 依然回傳 `True`（表示順利完成 check 動作），因此主程式的 `Errors` 計數不會增加。但此時 client 的訂閱已在 Broker 端因連線重置而消失，因此後續無法接收任何新訊息。
- **教訓**：
  1. **放寬 MQTT 限制**：由於我們已實作「直接串流寫入 Flash 檔案」的記憶體優化機制，應放寬 `simple.py` 的封包長度限制（例如放寬至 102400 或更大），使其能安全接收 96KB 的影像。
  2. **修復重連訂閱邏輯**：不能依賴 `umqtt.robust` 的自動無聲重連。應讓 `check_messages()` 正確反映連線失效，並由主程式重新呼叫 `connect` 進行完整的連線與訂閱；或者在 `robust.py` 重連成功後，重新執行訂閱。
  3. **主程式 Raw 2-bit Binary 解析需支援雙通道**：主程式的 `BMPDisplay._load_and_display_raw` 目前僅讀取前 48,000 位元組至黑白 Buffer。在修正 MQTT 後，必須同步修改該方法，連續讀入黑白與紅色兩個 48,000 位元組 Buffer，才能正常顯示三色畫面。

## 12. MQTT 本地套件匯入與工作目錄依賴
- **錯誤案例**：MQTT 初始化失敗時，Pico 顯示 `name 'MQTTClient' isn't defined`，因為 `core/mqtt_handler.py` 沒有先確認 `lib/umqtt` 本地套件目錄是否被包含在 `sys.path` 中，甚至缺少 `umqtt` 套件的 `__init__.py`。
- **後果**：程式會在 `MQTTHandler.connect()` 之前或之後直接拋出 `ImportError` / `NameError`，導致 MQTT 重連失敗且顯示錯誤頁面，儘管本地驅動程式已存在。
- **教訓**：在 MicroPython 專案中，**本地套件路徑必須明確載入並且需要 `__init__.py` 作為套件初始化檔案**。特別要避免依賴工作目錄或預設模組搜尋路徑的隱性行為，因為不同啟動方式（例如 REPL、腳本直接執行、從不同目錄開啟）會改變模組解析結果。
- **修正**：新增 `lib/umqtt/__init__.py`，並在 `core/mqtt_handler.py` 中加入 `_ensure_umqtt_package()`，將本地 `./lib` 插入 `sys.path`，同時保留 `umqtt.robust` / `umqtt.simple` 的自動 fallback。
