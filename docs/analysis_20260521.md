# MQTT 大檔案接收錯誤分析報告 (Analysis Report - 2026-05-21)

本報告針對發送 96KB 三色二進位影像檔 (.bin) 透過 MQTT 傳輸至 Raspberry Pi Pico W 時，主程式無法正常接收且無聲失效的問題進行深入分析，並提供具體建議與修復方案。

## 1. 問題現象描述

當透過 MQTT 發送 96KB 的三色二進位影像檔時，終端機顯示以下錯誤訊息：
```
[umqtt] ERROR: Message too large: 96000
[Main] Status: Loop #1320, Errors: 0, (1ms/check)
[Main] Status: Loop #1380, Errors: 0, (0ms/check)
[Main] Status: Loop #1440, Errors: 0, (0ms/check)
```
此後，Pico W 不再接收任何 MQTT 訊息，但主程式未崩潰，仍正常進入 check 迴圈，且錯誤計數 `Errors` 為 0。

---

## 2. 根本原因分析 (Root Cause Analysis)

經過代碼走讀與追蹤，此問題由以下三個層面的因素共同導致：

### A. `umqtt.simple` 的硬編碼長度限制
在 `lib/umqtt/simple.py` 第 210-212 行中，存在以下檢查：
```python
if sz > 65535: # Arbitrary limit for Pico safety, adjust if needed
    print("[umqtt] ERROR: Message too large: {}".format(sz))
    raise OSError(-1)
```
* **原因**：為了防止 MicroPython 因接收過大封包而記憶體溢出（`ENOMEM`），函式庫設定了 `65535` 位元組的硬性上限。
* **衝突**：我們發送的 800x480 三色紅黑 binary 檔案大小為：`(800 * 480 / 8) * 2 = 96,000` 位元組（黑白通道 48KB + 紅色通道 48KB）。因為 `96000 > 65535`，直接觸發此錯誤並拋出 `OSError(-1)`。

### B. `umqtt.robust` 重連機制的「訂閱遺失」陷阱
我們的 MQTT Client 使用了 `umqtt.robust`。在 `lib/umqtt/robust.py` 中：
```python
def check_msg(self, attempts=2):
    while attempts:
        self.sock.setblocking(False)
        try:
            return super().wait_msg()
        except OSError as e:
            self.log(False, e)
        self.reconnect()
        attempts -= 1
```
* **異常吞沒**：當 `simple.py` 拋出 `OSError(-1)` 時，該異常會被 `robust.py` 內部的 `except OSError` 補捉。
* **未重新訂閱**：`robust.py` 的 `reconnect()` 僅會重新建立 TCP 連線與 MQTT 登入，**並不會自動重新訂閱原有的主題**（`subscribe`）。
* **無聲失效**：由於異常在內部被攔截並完成了 socket 重連，對外（`core/mqtt_handler.py`）來說，`check_messages()` 依然回傳 `True`（表示順利完成 check 動作），因此主程式的 `Errors` 計數不會增加。但此時 client 的訂閱已在 Broker 端因連線重置而消失，因此後續無法接收任何新訊息。

### C. `BMPDisplay` 尚未支援 96KB 的雙通道渲染
即使我們放寬了 MQTT 的接收上限，目前主程式 `core/bmp_display.py` 中的 `_load_and_display_raw` 寫法如下：
```python
bytes_read = f.readinto(self.epd.buffer_black)
```
* **限制**：目前僅讀取了前 48,000 位元組至黑白 Buffer，而紅色 Buffer 會被直接清空為 0。
* **衝突**：96KB 的 binary 檔案包含了黑白與紅色兩個部分，這會導致即使接收成功，也只能顯示黑色部分，紅色通道的影像資料會被丟棄。

---

## 3. 建議與修復方案 (Proposed Solutions)

在不修改程式碼的前提下，建議後續進行以下三項修改：

### 方案 1：放寬 MQTT 訊息長度限制
將 `lib/umqtt/simple.py` 中的限制修改為相容 96KB 檔案的大小：
```diff
-        if sz > 65535: # Arbitrary limit for Pico safety, adjust if needed
+        if sz > 102400: # Allow up to 100KB for 3-color raw binary files (96,000 bytes)
```
*(由於我們已經在 `simple.py` 實作了分段寫入 Flash 的機制 `temp_mqtt_msg.bin`，放寬此限制不會對 RAM 造成任何額外壓力)*

### 方案 2：修正 MQTT 重新訂閱邏輯
為了避免重連後訂閱遺失，建議在 `core/mqtt_handler.py` 中，將 `check_messages` 修改為在發生 OSError 時主動標記連線中斷，或者在 `umqtt.robust` 重連後重新訂閱主題。
例如在 `core/mqtt_handler.py` 中：
* 捕捉重連狀態並在重連後重新執行 `subscribe`；
* 或者將初始連線的 `clean_session` 設為 `False`，且 Broker 需支援 Session 持久化（但主動重新訂閱是最穩健的做法）。

### 方案 3：更新 Raw Binary 顯示邏輯
修改 `core/bmp_display.py` 中的 `_load_and_display_raw` 方法，使其根據檔案大小自動適配雙 Buffer 讀取：
```python
with open(filepath, 'rb') as f:
    # 讀取黑白通道
    bytes_read = f.readinto(self.epd.buffer_black)
    
    # 若檔案大於 48,000 位元組，且 display 支援紅色 buffer，則讀取紅色通道
    if file_size >= 96000:
        f.readinto(self.epd.buffer_red)
    else:
        # 單色時清空紅色通道
        if hasattr(self.epd, 'imagered'):
            self.epd.imagered.fill(0)
```
